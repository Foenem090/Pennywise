# Penny Wise Database Migrations Guide (Alembic)

This document provides guidelines, procedures, and architectural requirements for managing schema migrations in Penny Wise using Alembic.

---

## 1. Overview & Architecture

Penny Wise uses **Alembic** for version-controlled, reproducible database schema migrations.

### Separation of Concerns: Application Runtime vs. Administrative DDL
- **Application Runtime (`DATABASE_URL`):**
  The FastAPI application connects to PostgreSQL using Neon's connection pooler (`-pooler.c-2.eu-west-2.aws.neon.tech`) with PgBouncer in transaction pooling mode.
- **Administrative Migrations (`DATABASE_URL_DIRECT`):**
  Penny Wise requires direct, unpooled PostgreSQL connections for administrative migrations and schema management. Schema migrations must be directed to the unpooled endpoint rather than PgBouncer.

---

## 2. Common Migration Workflows

Always execute migration commands from the `backend/` directory or provide `-c backend/alembic.ini`.

### Generating a New Migration
When models in `backend/app/models/` are modified, generate a new migration revision:
```bash
cd backend
alembic revision --autogenerate -m "describe_the_change"
```
To run autogenerate against an explicit database URL:
```bash
alembic -x url="sqlite:///./pennywise.db" revision --autogenerate -m "describe_the_change"
```

### Reviewing Autogenerated Migration Files
Autogenerated migrations must **always be manually reviewed** before committing:
1. Open the generated file in `backend/alembic/versions/`.
2. Verify table and column names, datatypes, and nullability.
3. Verify index names and uniqueness (`unique=True` vs `unique=False`).
4. Ensure both `upgrade()` and `downgrade()` functions are completely implemented and reversible.
5. Watch out for unsupported automatic operations (e.g., table renames may be interpreted as `drop_table` + `create_table` instead of `rename_table`).

### Upgrading a Development Database
To apply all pending migrations up to the latest revision (head):
```bash
cd backend
alembic upgrade head
```

### Inspecting Current Revision
To check which migration revision the target database is currently on:
```bash
cd backend
alembic current
```
To view migration history:
```bash
cd backend
alembic history --verbose
```

### Generating SQL Without Executing (Offline Mode)
Alembic can generate raw SQL scripts without connecting to a live database or executing any DDL:
```bash
cd backend
alembic upgrade head --sql
```
To save the generated SQL to a file for review:
```bash
cd backend
alembic upgrade head --sql > migration_plan.sql
```

## 3. Production Neon & Connection Architecture

### Why This Project Requires Direct Unpooled Connections for Migrations
Neon's default application connection string routes traffic through PgBouncer in **transaction pooling** mode (`-pooler`). While basic, single-transaction DDL operations can technically run through a transaction pooler, Penny Wise strictly requires direct, unpooled PostgreSQL connections (`DATABASE_URL_DIRECT`) for administrative migrations due to key operational and compatibility considerations:

1. **Session State Discarded Across Transactions:** In transaction pooling mode, server connections are returned to the pool as soon as a transaction ends. Migration scripts frequently set session-scoped parameters (e.g., `SET statement_timeout`, `SET lock_timeout`, `SET search_path`). In transaction pooling, these session settings do not reliably persist across successive transactions or statements.
2. **Non-Transactional Operations:** Critical schema operations—such as `CREATE INDEX CONCURRENTLY` or `VACUUM`—cannot run inside a transaction block in PostgreSQL and require an autocommit connection. Transaction poolers that enforce transaction framing can conflict with these statements.
3. **Lock Contention & Pool Exhaustion:** Complex, multi-statement migrations holding table-level locks can interact unfavorably with transaction pool limits, increasing the risk of deadlocks or pool exhaustion while locks are held.

**Enforcement Guard:**
Penny Wise's `backend/app/config.py` parses the target database hostname via `make_url()` and explicitly rejects Neon endpoints containing `-pooler`. Administrative migrations must always be supplied with an unpooled direct connection string via `DATABASE_URL_DIRECT` or `-x url=...`.

## 4. Production Stamping: A Separately Reviewed Operation

### Why `alembic stamp` Must Be Separately Reviewed
The production database in Neon already contains tables (`newsletter_subscribers` and `contact_inquiries`) created earlier by SQLAlchemy startup initialization.

- If you run `alembic upgrade head` on a database that already has those tables, PostgreSQL will fail with:
  ```text
  psycopg.errors.DuplicateTable: relation "newsletter_subscribers" already exists
  ```
- **What Stamping Does (and Does Not Do):**
  Stamping creates the `alembic_version` table (if not present) and records the baseline revision hash (`2354f5b41338`).
  - Stamping **does not execute** the baseline migration script.
  - Stamping **does not verify** that the production database schema actually matches the baseline revision.
  - Stamping **does not repair or reconcile** schema drift, missing columns, or mismatched constraints.

### Mandatory Pre-Stamping Safety Requirements
Before executing the baseline stamp on the production database, the following four conditions must be satisfied:

1. **Verified Backup or Recovery Point:** Confirm an independent data export (e.g. `pg_dump` via direct connection) or a verified Neon point-in-time recovery (PITR) restore point is established before performing any administrative action.
2. **Read-Only Schema Comparison:** Conduct a read-only comparison of the actual Neon production database schema against baseline revision `2354f5b41338`.
3. **Comprehensive Structural Verification:** Verify that production precisely matches the expected baseline across:
   - Table existence (`newsletter_subscribers`, `contact_inquiries`).
   - Column names, datatypes, lengths, and nullability constraints.
   - Primary keys (`id` on both tables).
   - Indexes and unique constraints (`ix_newsletter_subscribers_email` unique index, `ix_contact_inquiries_email`, and primary-key indexes).
4. **Explicit Human Approval:** Production stamping must never be automated in CI/CD, startup scripts, or deployment hooks. It requires explicit human review and sign-off once the pre-stamp audit confirms 100% schema alignment.

### The Stamping Command
Once prerequisites are verified and human approval is obtained, stamp the exact baseline revision:
```bash
cd backend
alembic stamp 2354f5b41338
```
Or with an explicit direct connection string:
```bash
cd backend
alembic -x url="$DATABASE_URL_DIRECT" stamp 2354f5b41338
```

After this initial baseline stamp is recorded on production, future migrations will apply incrementally using `alembic upgrade head`.
