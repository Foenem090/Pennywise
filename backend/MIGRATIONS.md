# Penny Wise Database Migrations Guide (Alembic)

This document provides guidelines, architectural rules, and safe operational procedures for managing schema migrations in Penny Wise using Alembic.

---

## 1. Overview & Architecture

Penny Wise uses **Alembic** for version-controlled, reproducible database schema migrations. Application models live in `backend/app/models/` and share `Base.metadata` from `backend/app/database.py`.

### Separation of Concerns: Application Runtime vs. Administrative DDL
- **Application Runtime (`DATABASE_URL`):**
  The FastAPI application connects to PostgreSQL using Neon's connection pooler (for example, hosts ending in `-pooler...neon.tech`) with PgBouncer in transaction pooling mode.
- **Administrative Migrations (`DATABASE_URL_DIRECT`):**
  Penny Wise requires direct, unpooled PostgreSQL connections for administrative migrations and schema management. Schema migrations must be directed to the unpooled endpoint rather than PgBouncer.

### Managed Application Tables vs. Neon Sample Table (`playing_with_neon`)
- **Application-Managed Tables:** `contact_inquiries` and `newsletter_subscribers` (defined in `backend/app/models/contact.py` and `backend/app/models/newsletter.py`, and established in baseline revision `2354f5b41338`) plus any future application models.
- **Neon Sample Table (`playing_with_neon`):**
  Neon provisions a default sample table named `playing_with_neon` in the production database. It is **not** managed by Penny Wise application models and **must not be manually deleted or modified** in production.
- **Alembic `include_object` Exclusion:**
  `backend/alembic/env.py` defines an `include_object(object, name, type_, reflected, compare_to)` callback that returns `False` when `type_ == "table" and name == "playing_with_neon"`, and `True` for everything else.
  - Both `run_migrations_offline()` and `run_migrations_online()` in `backend/alembic/env.py` register `include_object=include_object`.
  - All other tables (including `contact_inquiries` and `newsletter_subscribers`), indexes, columns, and constraints remain fully included in Alembic autogeneration and schema comparisons.

### Alembic Autogeneration Settings (`backend/alembic/env.py`)
Both offline and online `context.configure(...)` calls enable:
- `render_as_batch=True`: Emits `op.batch_alter_table(...)` blocks in autogenerated revisions so schema alterations remain compatible with local SQLite testing as well as PostgreSQL.
- `compare_type=True`: Detects column datatype and length changes during autogeneration and `alembic check`.
- `compare_server_default=True`: Detects server-side default expression differences during autogeneration and `alembic check`.

## 2. Safe Migration Workflows

> **Working Directory & `.env` Loading:**
> Penny Wise's `Settings` (`backend/app/config.py`) loads `env_file=".env"` relative to the **current working directory**. While `backend/alembic.ini` resolves `script_location = %(here)s/alembic` regardless of working directory, running `alembic -c backend/alembic.ini` from the repository root will not read `backend/.env`. Normally run all migration commands from the `backend/` directory (`cd backend`), unless you supply environment variables or `-x url=...` explicitly.

### Generating a New Migration & Autogeneration Safety
When models in `backend/app/models/` are changed, generate a new migration revision with `alembic revision --autogenerate`.

> **CRITICAL AUTOGENERATION WARNING:**
> `alembic revision --autogenerate` connects to and inspects **whichever database the resolved migration URL points to** (`DATABASE_URL_DIRECT` takes precedence over `DATABASE_URL`).
> - **Never allow autogeneration to inspect production unintentionally** (for example, by running plain `alembic revision --autogenerate` when `backend/.env` has `DATABASE_URL_DIRECT` pointed at production Neon).
> - **Explicitly select an isolated development or staging database** (such as `-x url="sqlite:///./pennywise.db"` or a dedicated non-production PostgreSQL URL) before generating a revision.
> - **Ensure the selected database is already at the current Alembic `head`** (`alembic -x url=... upgrade head` beforehand); otherwise Alembic may fail or produce misleading diffs.
> - **Review every generated migration manually** before committing or applying it.

Example using the isolated local SQLite development database from `backend/`:
```powershell
cd backend
alembic -x url="sqlite:///./pennywise.db" upgrade head
alembic -x url="sqlite:///./pennywise.db" revision --autogenerate -m "describe_the_change"
```

### Reviewing Autogenerated Migration Files
Autogenerated migrations must **always be manually reviewed** before committing or applying:
1. Open the generated file in `backend/alembic/versions/`.
2. Verify table and column names, datatypes, and nullability.
3. Verify index names and uniqueness (`unique=True` vs `unique=False`).
4. Ensure both `upgrade()` and `downgrade()` functions are completely implemented and reversible.
5. Watch out for unsupported automatic operations (e.g., table renames may be interpreted as `drop_table` + `create_table` instead of `rename_table`).
6. Verify that no migration attempts to create, alter, or drop `playing_with_neon`.
7. Use `alembic check` to check for schema drift against the configured database (passing `-x url=...` for non-production targets when `DATABASE_URL_DIRECT` is configured).

### Inspecting Revisions
To check which migration revision a target database is currently on:
```powershell
cd backend
alembic current
```
To view local migration history:
```powershell
cd backend
alembic history --verbose
```

### Generating SQL Without Executing (Offline Mode)
Alembic can emit raw SQL DDL without executing statements against a live database:
- Running `alembic upgrade head --sql` emits SQL from **`base` to `head`** because offline mode does not read `alembic_version` from a live database. On an already-baselined project, that output includes the initial baseline table creation (`2354f5b41338`) in addition to newer revisions.
- For **incremental production SQL review**, specify the starting revision explicitly — for example, when production is at baseline `2354f5b41338`:

```powershell
alembic upgrade 2354f5b41338:head --sql
```

- Once production has advanced beyond the baseline, replace `2354f5b41338` with production's actual current revision (verified beforehand with `alembic current`).
- **Dialect & URL requirement:** Even in offline `--sql` mode, `backend/alembic/env.py` calls `get_migration_url()` to validate the URL and choose the SQLAlchemy dialect. Ensure the intended PostgreSQL direct migration URL is active (via `DATABASE_URL_DIRECT` or `-x url="<DATABASE_URL_DIRECT>"`, avoiding `-pooler` hosts) so Alembic generates PostgreSQL DDL rather than accidentally emitting SQLite DDL.

To save the generated incremental PostgreSQL plan to a file for review:
```powershell
cd backend
alembic upgrade 2354f5b41338:head --sql > migration_plan.sql
```

### Complete Safe Migration Workflow (Development to Production)
Follow this end-to-end process for every schema change:
1. Ensure existing code is backed up / cleanly committed in Git, then make the intended model changes in `backend/app/models/`.
2. Select an isolated development or staging database (local SQLite or a dedicated non-production PostgreSQL database / branch — never production).
3. Confirm its current Alembic revision (`alembic -x url=... current`) and upgrade it to `head` if needed.
4. Generate the new migration against that isolated database (`alembic -x url=... revision --autogenerate -m "describe_the_change"`).
5. Review the complete generated migration file in `backend/alembic/versions/` against the review checklist above (confirming `playing_with_neon` does not appear).
6. Inspect the generated incremental PostgreSQL SQL via offline mode (`--sql`) where appropriate.
7. Run the migration test suite from `backend/` (`python -m pytest tests/test_migrations.py -v`).
8. Test `upgrade`, `downgrade`, and `upgrade` again against a separate non-production database to verify reversibility and data safety.
9. Run `alembic check` against the test database (`alembic -x url=... check`) to confirm zero schema drift.
10. Obtain a verified independent production backup before **every** production migration (an independent `pg_dump` via the direct PostgreSQL connection and/or a verified Neon PITR restore point). **This production backup requirement applies to every future production migration, not just the original baseline stamp.**
11. Apply the approved migration to production using the direct unpooled database URL (`alembic upgrade head` via `DATABASE_URL_DIRECT`, or `alembic -x url="<DATABASE_URL_DIRECT>" upgrade head`).
12. Verify the resulting production revision using `alembic current` and perform read-only schema/data checks (confirming expected tables, indexes, preserved application rows, and `playing_with_neon` untouched).

## 3. Production Neon, URL Resolution & Connection Architecture

### Migration Database URL Resolution Precedence
`backend/alembic/env.py` resolves the target database URL exclusively through `Settings.get_migration_database_url()` (`backend/app/config.py`) in strict priority order, with no silent fallback if a higher-priority value is invalid:

1. **Explicit CLI override (`-x url=...`)** (or `config.attributes` URL override used by automated tests).
2. **`DATABASE_URL_DIRECT`** (preferred environment variable for administrative PostgreSQL migrations).
3. **`DATABASE_URL`**, provided it is not a pooled PostgreSQL URL (for example, local SQLite `sqlite:///./pennywise.db` or a direct PostgreSQL endpoint).

Key rules enforced by `Settings.get_migration_database_url()` and `Settings.get_migration_connect_args()`:
- Runtime application traffic uses the pooled `DATABASE_URL`; migrations require an unpooled/direct PostgreSQL connection (`DATABASE_URL_DIRECT` in production).
- Pooled Neon URLs (hostnames containing `-pooler`) are **rejected** for migrations.
- `backend/alembic.ini` contains a placeholder `sqlalchemy.url = driver://user:pass@localhost/dbname` which is **not** the effective database URL because `env.py` always resolves the URL through application `Settings`.
- Legacy `postgres://` and bare `postgresql://` schemes are normalized to `postgresql+psycopg://`, and PostgreSQL migration connections receive `connect_timeout = DB_CONNECT_TIMEOUT_SECONDS` (SQLite keeps `check_same_thread=False`).

### Why Transaction Pooling Is Unsuitable for Migrations
Neon's default application connection string routes traffic through PgBouncer in **transaction pooling** mode (`-pooler`). While simple single-transaction DDL might appear to work through a pooler, Penny Wise strictly requires direct, unpooled PostgreSQL connections (`DATABASE_URL_DIRECT`) for administrative migrations because of:

1. **Session State Discarded Across Transactions:** In transaction pooling mode, server connections return to the pool at transaction boundaries. Migration operations that rely on session-scoped settings (e.g., `SET statement_timeout`, `SET lock_timeout`, `SET search_path`) do not reliably retain session state across statements or transactions.
2. **Non-Transactional Operations:** Operations such as `CREATE INDEX CONCURRENTLY` or `VACUUM` cannot run inside a transaction block in PostgreSQL and require a direct connection capable of autocommit execution.
3. **Lock Contention & Pool Exhaustion:** Multi-statement schema migrations holding table locks can interact poorly with PgBouncer pool limits, increasing deadlock or pool-exhaustion risk.

**Enforcement Guard:**
`Settings.get_migration_database_url()` in `backend/app/config.py` parses the resolved URL with SQLAlchemy's `make_url()` and inspects the hostname (`parsed_url.host`), raising a `RuntimeError` without leaking credentials if `"-pooler"` appears in the hostname.

> **WARNING: Never rerun `alembic stamp 2354f5b41338` against production as part of routine migration operations.**
> `alembic stamp` updates the revision recorded in `alembic_version` **without** executing the migration's `upgrade()` or `downgrade()` schema operations. Rerunning `alembic stamp 2354f5b41338` on production after later migrations have been applied would reset Alembic's version record back to the baseline without rolling back schema changes, corrupting migration history.

Future production schema changes must apply incrementally via `alembic upgrade head` using the workflow in Section 2.

### Historical Reference: Completed Pre-Stamp Rationale & Checklist

The details below explain why the initial production baseline required stamping rather than running `upgrade head` and preserve the checklist completed prior to stamping.

#### Why `alembic stamp` Was Required Once at Baseline
Production Neon originally contained application tables (`newsletter_subscribers` and `contact_inquiries`) created earlier by SQLAlchemy startup initialization before Alembic was introduced.
- Running `alembic upgrade head` against an unstamped database that already had those tables would fail with:
  ```text
  psycopg.errors.DuplicateTable: relation "newsletter_subscribers" already exists
  ```
- **What Stamping Does (and Does Not Do):**
  `alembic stamp` creates the `alembic_version` table (if absent) and records the specified revision hash (`2354f5b41338`).
  - It **does not execute** the migration script's DDL.
  - It **does not verify** that live schema matches the baseline script.
  - It **does not repair or reconcile** schema drift, missing columns, or mismatched constraints.

#### Completed Pre-Stamp Verification Checklist *(Historical Reference — Completed)*
1. **[Completed] Verified Backup / Recovery Point:** An independent production `pg_dump` was created using the direct connection, encrypted copies were established, and a separate local database restore was successfully tested before the production baseline stamp.
2. **[Completed] Read-Only Schema Comparison:** Live Neon schema compared read-only against baseline revision `2354f5b41338` (confirming only Neon's unmanaged `playing_with_neon` differed before `include_object` exclusion was added).
3. **[Completed] Comprehensive Structural Verification:** Verified table existence (`newsletter_subscribers`, `contact_inquiries`), column datatypes/nullability, primary keys (`id`), and indexes (`ix_newsletter_subscribers_email` unique index, `ix_contact_inquiries_email`, and `id` indexes).
4. **[Completed] Explicit Human Approval & Verification:** Executed with explicit approval and verified afterward read-only (`alembic_version == '2354f5b41338'`).
